1. The Big Picture: What We Are Building ("In Short")

ArchViz started as a modern visual cloud design tool that lets engineers draw cloud architectures on an interactive canvas, test latency and costs, and deploy infrastructure via Terraform.

ArchViz Autonomous is the next-generation evolution: an autonomous 24/7 AI Cloud Engineer that continuously monitors customer AWS infrastructure. If a database maxes out on connections, a container enters a crash loop, a security group is left open to the world, or an API begins timing out, the system automatically detects the incident, finds the exact root cause, writes a verified Terraform fix, and alerts the user with a single [Approve & Apply Fix] button.

1. Krish's Engine (YOU)
Platform Integration & Telemetry: Connects to the user's AWS account, catches alarms, collects 30m CloudWatch logs + 60m CloudTrail events, attaches the visual Canvas Graph, and hands it over.
2. Gargi's Engine
Diagnostic AI (RCA): Deduplicates cascading alarms, uses RAG over 25 AWS troubleshooting runbooks, pinpoints the root failing resource, and computes confidence score (0-100%).
3. Sweta's Engine
Remediation & Safety: Takes Gargi's diagnosis, writes the Terraform code diff + AWS SDK command, passes 3-Gate safety checks, and runs pre-flight latency/cost simulations.
Krish's Clear Boundary
Your responsibility is strictly getting the real logs and events from the user's AWS account and delivering a clean, standardized data packet to Gargi. You do not write Gargi's diagnostic prompts or Sweta's Terraform fix code. You build the robust highway that delivers live AWS truth into their AI modules.

1
Dynamic Multi-Tenant AWS Account Access (src/aws/credentials.ts):
Users can authenticate either via direct IAM keys (AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY) or via enterprise cross-account STS AssumeRole (RoleArn + ExternalId). The system creates temporary 15-minute read-only sessions with zero credentials permanently stored.
2
24/7 Autonomous Alarm Webhook Listener (src/api/webhooks.ts):
An HTTP endpoint POST /api/webhooks/aws-alarm that receives alerts from AWS EventBridge, CloudWatch Alarm state changes, AWS SNS topic notifications, or direct API triggers whenever an outage begins.
3
Intelligent Log Group Auto-Discovery (src/collector/cloudWatchCollector.ts):
Instead of guessing, the collector inspects the failing AWS resource ARN and probes the user's AWS account using DescribeLogGroups for Lambda (/aws/lambda/*), RDS (/aws/rds/instance/*), ECS (/ecs/*), and API Gateway (API-Gateway-Execution-Logs_*), ensuring it finds real logs on live AWS accounts.
4
Trailing 30-Minute CloudWatch Log Pre-Filter (src/collector/logFilter.ts):
CloudWatch logs are full of noise ([INFO] Application started, GET /health 200 OK, heartbeats). Your pre-filter strips out all noise lines and extracts only ERROR, FATAL, WARN, and TIMEOUT lines to keep Gargi's LLM context clean and cost-effective.
5
Trailing 60-Minute CloudTrail Configuration Lookups (src/collector/cloudTrailCollector.ts):
Queries AWS CloudTrail for the trailing 60 minutes to uncover recent deployments and administrative changes (e.g., AuthorizeSecurityGroupIngress, ModifyDBParameterGroup, RegisterTaskDefinition, UpdateService). It extracts user identities and full JSON request parameters.
6
ArchViz Canvas Graph Topology Attachment (src/types/canvasGraph.ts):
Attaches the user's architecture diagram topology (all nodes with id, type, awsResourceId, and edges with source and target). The resource indexer maps failing AWS resource ARNs directly to Canvas Node IDs so Gargi can trace upstream/downstream connections.

4. How Gargi Will Link Her Engine With Your Code

Gargi connects to your code using a single standardized contract called Handoff 1. You deliver the raw data; her system consumes it.

The Exact Handoff 1 Data Contract (src/types/alertPayload.ts)
Whenever an incident triggers, your backend service produces this exact TypeScript object and passes it to Gargi: 
export interface AlertPayload {
  incidentId: string;
  triggeredAt: string;
  activeAlarms: Array<{
    alarmId: string;
    alarmName: string;
    nodeId: string;          // Maps directly to ArchViz canvas node ID
    awsResourceId: string;   // Full AWS ARN or physical ID
    metricName: string;
    metricValue: number;
    threshold: number;
    timestamp: string;
  }>;
  cloudWatchLogs30m: Array<{
    timestamp: string;
    nodeId: string;
    awsResourceId: string;
    level: 'ERROR' | 'FATAL' | 'WARN' | 'TIMEOUT';
    message: string;
  }>;
  cloudTrailEvents60m: Array<{
    eventId: string;
    eventTime: string;
    eventName: string;
    awsResourceId: string;
    userIdentity: string;
    requestParameters: Record<string, unknown>;
  }>;
  canvasGraph: {
    nodes: Array<{ id: string; type: string; awsResourceId: string; data: Record<string, unknown> }>;
    edges: Array<{ id: string; source: string; target: string }>;
  };
}

5. What Gargi Does With Your Data (Her Diagnostic Scope)

Once your backend feeds the AlertPayload into Gargi's function, her code executes four sequential tasks:

A
Graph Alert Deduplication: When an RDS database fails, the connected Lambda and API Gateway also start throwing errors, creating 10+ alarms. Gargi uses the canvasGraph you provide to traverse downstream edges and find the single deepest root resource (collapsing 10 alarms into 1 root incident).
B
Runbook Search via RAG: For that failing resource, her RAG retriever takes the pre-filtered logs and CloudTrail changes you gave her and queries her vector database of 25 AWS troubleshooting runbooks to find the root cause.
C
Confidence Scoring (0% to 100%): She calculates a mathematical confidence score: 40% if an exact error code matches, 25% if a CloudTrail change happened shortly before the alarm, 20% if metrics crossed 90%, and 15% based on runbook similarity.
D
Handoff 2 to Sweta: Gargi packages her diagnosis into DiagnosisReport (containing failingNodeId, scenarioType, confidenceScore, rootCauseSummary, and recommendedFixIntent) and passes it to Sweta.
